Windows 端「添加新设备」重做方案

BlueSelf 跨端文件传输 · AddDeviceView 重做 + 设备图标分类协议升级（含 Android 端一处小改）

状态：待确认 2026-08-28 前置结论已定：配对记录退化 + legacy link key 被拒 → 重配已解决连接问题

1三个问题的根因

根因一电脑图标失效

旧方案"名字加 Windows"从未真正写回系统蓝牙名——LocalDeviceName() 只是生成了字符串，仅用于 PC→手机 TXT 帧的 sName。而 Android 入库的 deviceType 取自扫描时的名字 + CoD：广播名无关键词、CoD 又不可靠（Realtek × Qualcomm），就被存成 PHONE，且从不修正。

根因二PC 扫不到新设备

FindAllAsync(AssociationEndpoint) 只翻系统 AEP 缓存、不触发射频 inquiry，未配对手机很快被缓存驱逐；再叠加 IsLikelyPeerDevice 按"名字不像就丢"的过滤，一加 11 即使被看到也会被滤掉。

根因三扫描图标不正常

AddDeviceView.xaml 状态横幅左侧的 TextBlock 没有绑定任何 glyph 字符（Text 缺失，只绑了可见性），所以显示异常；顶栏按钮误用"刷新设备列表"文案，且无扫描中的动态反馈。

2方案总览

WIN ADeviceKind 四信号分类器

词表 + CoD + BlueSelf 服务命中 + sName，两端词表对齐的唯一实现

WIN BDeviceWatcher 流式扫描

真实射频发现，属性直读不建对象，800ms 去重即时上屏，直接 PairAsync 配对

WIN CAddDeviceView 重做

旋转扫描图标、流式列表、空态引导、行尾按钮三态

ANDsName 事后校准

Android 收到 TXT 时按 sName 重判并回写 Room，存错也能自愈

关键设计决策：不做"PC 程序化改系统蓝牙名"（需管理员 + 重启蓝牙栈，且对手机端已保存记录无效），改走消息层 sName 校准：零权限、即时生效、双向闭环，且协议字段已存在。不引入 32feet 等第三方库；不动现有 RFCOMM/协议帧。

四信号表决

信号权重来源说明
① 名字关键词高蓝牙名保留现词表，补 laptop/notebook/desktop/台式/笔电/笔记本，两端完全对齐
② CoD 主类中Class of Device名字无关键词时的兜底；本机组合上报不可靠，不单独定论
③ BlueSelf 服务命中高SDP 缓存 / 连接事实新增权威信号：能连上的设备一定装了 BlueSelf，独立于名字与 CoD

pc     ← ①命中PC词，或 ④sName命中PC词，或（②=Computer 且 ③有服务）
tablet ← ①命中平板词，或 ④sName命中平板词
phone  ← ①命中手机词，或（②=Phone 且 ③有服务）

3发现机制：旧路径 vs 新路径

维度现状（FindAllAsync）重做后（DeviceWatcher）
是否触发真实射频扫描否（翻系统 AEP 缓存）是（系统级 discovery）
未配对设备可见性短暂可见后消失（缓存驱逐）持续事件流，Removed 前一直在
结果上屏12s 超时后一次性~0.8s debounce 流式上屏
单设备开销每台一次 FromIdAsync零额外对象创建，纯属性读取
配对入口FromIdAsync 后 PairAsyncwatcher 的 DeviceInformation 直接 PairAsync（SSP 新密钥，绕开 legacy key 拒绝路径）
AQS 限定经典蓝牙 AEP +（CanPair OR IsPaired 放宽，保证已配对设备可见可重连）；地址/CoD 从事件属性直读，实现时先打印候选属性再固化解析，防驱动差异。
